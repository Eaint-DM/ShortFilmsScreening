## S02 — Short-film screening programme

**Scenario:**

A film club organiser needs to choose fictional short films and estimate viewing time. The seeded film catalogue gives each film's code, title, runtime in minutes and genre. The organiser creates a screening programme and edits its selected films and screening counts; the catalogue remains reference data.

**Workflow:**

1. The frontend calls `GET /api/films` to display the catalogue. Selecting a film calls `GET /api/films/{filmCode}` to display its runtime and genre.
2. The frontend creates a mock session code and sends it as `X-Session-Code` in `POST /api/screening-programmes`. The API creates a programme for that session, or returns its existing programme, and provides its `programmeCode`. Every subsequent programme request uses the same header.
3. To add a film, the frontend calls `POST /api/screening-programmes/{programmeCode}/items` with a body such as `{"filmCode":"FILM-001","screeningCount":1}`.
4. The frontend calls `GET /api/screening-programmes/{programmeCode}` to display saved films, screening counts and total programme minutes.
5. To change a count, the frontend calls `PUT /api/screening-programmes/{programmeCode}/items/{filmCode}` with a body such as `{"screeningCount":2}`, then calls `GET /api/screening-programmes/{programmeCode}` to display the updated programme.
6. To remove a film entry, the frontend calls `DELETE /api/screening-programmes/{programmeCode}/items/{filmCode}`, then calls `GET /api/screening-programmes/{programmeCode}` again.

The backend saves the catalogue, programme and entries in the database. It calculates total programme minutes using `sum(stored film runtime × saved screening count)`; the frontend displays the API's result. Both adding and changing a film require a whole-number screening count from 1 to 3. Invalid counts produce a suitable 4xx validation error and leave saved entries and the total unchanged.

**Evidence cases:**

1. Seed `FILM-001` with a runtime of 12 minutes and `FILM-002` with a runtime of 8 minutes. Add one screening of each. Show both saved entries in the browser and `GET /api/screening-programmes/{programmeCode}` response; verify `12 × 1 + 8 × 1 = 20 minutes`.
2. Change `FILM-001` to two screenings using `PUT`. Retrieve the programme and verify its saved count and total of `12 × 2 + 8 × 1 = 32 minutes` in the API response and browser.
3. Remove `FILM-002` using `DELETE`. Retrieve the programme and verify that only `FILM-001` remains with two screenings and `12 × 2 = 24 minutes`.
4. Try to change `FILM-001` to zero screenings using `PUT` with `{"screeningCount":0}`. Record the actual 4xx validation response and frontend feedback. Retrieve the programme again and confirm that its saved count remains two and its total remains 24 minutes.

Use the same mock session for these checks. Record the API requests and responses and corresponding browser behaviour. The approved AA-02 brief governs the common configuration, debugging, contribution and submission evidence.

**Contribution areas:**

1. **Frontend:** Build film browsing, runtime and genre details, and programme controls. Connect them to the API and display screening counts, updated minutes and errors.
2. **Backend and data:** Seed films; implement catalogue and programme endpoints; save entries; validate screening counts; and calculate duration from stored runtimes.
3. **Configuration, integration and testing:** Run the frontend, API and database together; trace programme requests; verify duration and error cases in the API and browser; and document a real issue, its fix and its retest.

These are work areas for a group of three, not fixed individual roles. Agree shared interfaces and document each student's own contribution as required by the brief.
